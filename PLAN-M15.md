# PLAN-M15 — Live desktop mode (exit demo)

**Status: implemented + verified (shell/NSIS packaged walk pending).**
Companion spec for the M15 box in PLAN.md §15. Core/web slices are
unit-verified; the Tauri slice is validated by the windows-build run and the
local packaged-boot walk (F below).

## Problem

The packaged desktop app boots **demo mode by default** (`DEMO_MODE` unset =
on): in-memory DB, fake keychain, `/v1/dev/pair-code` seam. Demo data dies
with the process and nothing touches the OS keychain or disk — fine for a
webapp container, wrong for the actual desktop product. The blocker was not
the config: a **live core deliberately exposes no pairing-code surface**
(the demo seam is demo-only by contract), and the designed device surface —
the **tray** — was listed "not-yet-implemented" in `shell/src-tauri/src/lib.rs`.
So live mode existed but could not be *entered* from the desktop app: no
persistent data dir was wired, no env flipped live, and no UI could show the
user the code.

## Decisions

1. **Packaged shell boots LIVE by default.** `PARTNER_DEMO_MODE=1` restores
   the historical in-memory demo boot (dev, webapp container, CI smoke).
   Raw `core` boots stay demo-by-default — unchanged for tests/dev.
2. **Live data lives under the per-user app-local data dir**
   (`app_local_data_dir()` → `%LOCALAPPDATA%\dev.ne1.partner` on Windows):
   `partner.db` (whole-file encrypted, key in the OS keychain service
   `partner` / account `db-key`) and `skills/`. NOT the install dir —
   upgrades replace `resources/` and must never touch user data.
3. **Device pairing channel (core).** `PARTNER_DEVICE_SECRET` (per-boot,
   CSPRNG, generated by the shell) enables `GET /v1/pair/device`, guarded by
   header `x-partner-device` (timing-safe compare). It issues the normal
   single-active 120s code; the code still dies with the process. Absent
   secret = route does not exist → a bare live core still exposes no code
   surface (existing guarantees intact; demo seam untouched and still
   verified demo-only).
4. **Tray = the live pairing surface.** "Show pairing code…" fetches a fresh
   code over the device channel and shows a native dialog (worker thread —
   the blocking dialog never freezes the main thread). Plus "Open Partner"
   and "Quit". Rust-only: no webview IPC, no ACL changes.
5. **Web PairGate is mode-aware.** It probes `/v1/health`; in live mode the
   copy points at the tray and the demo-code button is not rendered (only
   confirmed-demo cores show it). One code path for every client (the shell
   window and any browser on loopback): tray code → paste → pair.
6. Not in scope (follow-ups): auto-pairing the shell's own webview,
   clipboard copy in the tray, autostart/updater/restart policy (unchanged
   "future milestones"), migration from demo (demo is throwaway by design).

## Files

- `core/src/config.ts` — `CoreConfig.deviceSecret` (`PARTNER_DEVICE_SECRET`).
- `core/src/http/server.ts` — `CoreAppOptions.deviceSecret` +
  header-guarded `GET /v1/pair/device` (audit `pair.issue.device`, actor
  `shell`, empty details).
- `core/src/index.ts` — wiring + boot hint names the real code surface.
- `core/test/helpers.ts` / `server.test.ts` — harness option + 5 tests
  (absent→404; live+secret still hides the demo seam; wrong secret→401
  without rotating; tray code flows through POST /v1/pair; audit row shape).
- `shell/src-tauri/Cargo.toml` — tauri `tray-icon`/`image-*` features,
  `tauri-plugin-dialog`, `uuid` (v4), `ureq` (no TLS — loopback only).
- `shell/src-tauri/src/lib.rs` — live env (DEMO_MODE=0, DB_PATH/SKILLS_DIR
  under app-local data, secret), tray menu + pairing dialog.
- `web/src/lib/api.ts` — `fetchCoreHealth`.
- `web/src/PairGate.tsx` — live-aware copy + demo affordance gating.
- `web/test/api.test.ts` — `fetchCoreHealth` unit tests.
